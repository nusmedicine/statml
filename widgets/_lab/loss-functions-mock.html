loss-functions · the design picks, drawn to scale

The picks for the loss-functions widget, slot 54: three pages from PHM5005 05-4, cells 30–40. Regression (MSELoss, cells 31–33), Single-label (CrossEntropyLoss, cells 34–36), Multi-label (BCEWithLogitsLoss, cells 37–39, which cell 37 says serves the binary case too). Cell 30's table has one row per task, and that table is the rail. Every stage is drawn at the real 550 stage width, and the pages that change with the frame at 770 as well, on the geometry the deep-learning widgets share: PAD 14, GAP 22, usable width 522 at 550 and 742 at 770.

The structure of every page is Kenneth's own figure (_lab/figs/dl-loss-mse.png, dl-loss-ce.png, dl-loss-bce.png): a vertical flow with an Output (N) row carrying the class letters over the model's scores and a shape/dtype line under it, and a Target row with its own shape/dtype line. Those two strings are the anchor of the whole widget — [batch, N], float32 against [batch], long for CrossEntropyLoss, and [batch, N], float32 for BCEWithLogitsLoss — so they are on every page here. The probability row follows the convention support-layers already set for softmax (main.js 810–824): the row sum sits in a column outside the tensor, unfilled, because it is a reading of the row rather than one more probability.

Colour: the model's scores --c-group-a; every computed row — probabilities, per-class terms, gaps, squares — --c-empirical; the target, which is the fixed thing the scores are judged against, --c-reference; the held or dragged element and its point on the curve --c-highlight; torch's own error string --c-extreme; the curve itself --c-empirical, as curvePanel draws it in support-layers. Nothing on any page is random, so the widget takes no seed.

§1 · The rail at the real 300px

(a) the task faces. A one row of three, the notebook's own three rows — Regression · Single-label · Multi-label. B a w-seg-grid of two rows with the long face Binary / multi-label spanning, which is cell 37's claim that one function serves both. Both are the shell's own DOM and CSS, so what truncates here truncates in the widget.

(b) the cross-task contrast. A each option's detail line, one visible at a time. B a readback case table (core's w-readback, the one declaration is linear-regularization/main.js:541) with the three tasks as rows and one column holding the function applied inside the loss and the target the loss wants, the chosen row lit. Principle 3.4g: the shape says it before the reader does anything, and the confusion this widget exists for is exactly a confusion between two rows of that table.

(c) the per-page controls. A the tensors as torch prints them — a text field per tensor, plus the label control each page needs. B one Class segmented (which element is held) and one Score slider, shared across the three pages. Then the whole rail for the longest page, Multi-label, beside the shortest stage in the widget.

§2 · The Single-label stage

Cell 36: scores [5.0, 0.5, 0.1], label 0, loss 0.0184 — a confident right answer with nothing to watch at rest, which is why the drag is the control that carries the idea. (a) the scores row: A bars with a zero line, one per class under the letters, the value printed at the bar's end and the bar's top as the drag target; B the sibling widgets' cell grid, one number per cell, dragged to scrub the number. (b) the curve panel: A right of the rows; B below them across the width.

The recommended combination three times: at rest, settled, and settled with the score for class A dragged down to 1.0 (measure script §2: p 0.4967, loss 0.6997). A drag on a finished figure keeps it finished (principle 4.4) and moves the p row, the lit probability, the number and the point on the curve together.

(c) what the drag does to the axis. Principle 2.5 — fix the frame, not the data. Left, the bar axis is fitted to the values on screen, so dragging class A from 5.0 to 1.0 rescales the whole band and the two bars the reader did not touch grow. Right, the axis is fixed over the range the drag reaches, −2 to 6, so only the dragged bar moves. The bar heights are measured under each.

§3 · The Multi-label stage

Cell 39: scores [0.2, -1.0, 0.5, 2.0, -0.3], y = [0, 1, 1, 0, 0], loss 1.0534. Five bars, the sigmoid row, the five 0/1 chips with B and C filled, the probability given to each class's own label, the per-class −log p and their mean; the curve carries five points and lights the held one. A no sum column. B the sum in the same column position the Single-label page uses, unfilled and outside the tensor, reading 2.7476 where softmax's reads 1.0000.

§4 · The Regression stage

Cell 33: y_pred [2.5, 0.0, 2.1], y_true [3.0, -0.5, 2.0], loss 0.1700. The target is a tick on the same axis as the bar, and the gap is the bracket between the bar's top and the tick — the one page where the target can be drawn on the scores' own axis, because it is measured in the same units. Then the squared row: A the square as an area whose side is |gap| at the bars' own px-per-unit; B cells carrying gap, gap² and the mean as numbers.

§5 · The case that fails

Principle 2.6. The target's dtype as a control on the two classification pages. A a dtype segmented long · float32 under the label control, where the wrong arm prints torch's own message in the loss row's place and no number. B no control, the dtype rule as a readout note only. Both error strings are torch 2.14's own, printed by _lab/dl-loss-torch.py on 2026-09-11 (the first draft of this page quoted two of them from memory, and both were wrong).

§6 · The curve panel's own axis

A the −log p curve: loss against the probability given to the true label, p on x from 0 to 1 and loss on y clipped at 5. It is the same curve on both classification pages — CrossEntropyLoss enters it at softmax's true-class probability, BCEWithLogitsLoss five times at sigmoid(z) or 1 − sigmoid(z). B loss against the dragged score z, a different curve per page and per held element. Both drawn at cell 36's values and with the score for A dragged to 1.0.
