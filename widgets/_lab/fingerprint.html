Rendering fingerprint

Hashes each widget's canvas at a fixed state and compares against a stored baseline. Pixel-identical output is the only honest proof that a refactor changed nothing — “looks the same” is not, and screenshots of an animating figure are worse than useless.

Run before a refactor, run after. If a state DIFFERS and you did not mean to change it, you have found a regression. If you did mean to change it, press Copy new baseline and paste over widgets/_lab/fingerprint-baseline.json in the same commit as the change — so the diff records that the rendering moved and why.

Two kinds of state. A settled state passes shown= so the figure is fully built and nothing is moving. A driven state carries drive — this harness replaces the frame clock with a queue it steps by hand, performs an action, and advances a fixed number of fixed-length frames before hashing. Seeded data plus a controlled clock makes a mid-animation frame just as reproducible as a settled one.

The action is a drive button or a control. { click: "run" } presses .w-drive .w-btn[data-key="run"]; { set: { against: "risk" } } works the parameter control itself, found by its data-param. The second exists because a widget may decline drive buttons entirely (principle 4.5) and ease on a toggle instead — widget 12 does — and such a widget had no way to be driven at all, so its transitions carried no coverage while check.mjs still demanded some. Both forms work in before steps, and one step may do both.

Driven states exist because settled ones cannot see anything that is only drawn while something is moving. A coordinate-system change once left every falling ball six columns off-centre and every settled state still matched, because no settled state has a ball in flight. check.mjs now requires each widget with an animation to carry at least one driven state.
