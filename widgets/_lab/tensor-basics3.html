tensors · Basics — the stage sized to its content, and the index as an expression

Kenneth's third look, on the built round 7: the four regions waste most of the stage at every rank but 4; the roles line and torch.Size crowd the drawing; the index is still rail rows, not the expression T[ _, _, _ ] that was picked; and nothing on the stage says which row is the tensor and which is the index. What went wrong in the build: the 2 × 2 was drawn as a fixed grid over a fixed stage height sized by rank 4, so at rank 3 each region is two-thirds air; and the expression control was dropped because core has no control that renders text between fields on one line. Both are design decisions, not constraints, and both are mocked here.

§1 · The stage, sized to its content — the same four states at 550px

Two rows with headers, Tensor and Index, each a band across the full width with its name at the left and, on the Index row, the expression it evaluates. Inside a row the drawing sits left and the print right, separated by a hairline, both top-aligned. The row is as tall as its content — the taller of drawing and print, plus padding — so the stage height follows the rank: about 300px at rank 1–2, 380 at rank 3, 560 at rank 4. The page grows only when the tensor does (bayesian's precedent: height is a function of the parameters). The roles line and torch.Size sit 18px under the drawing on their own baseline grid. The whole-tensor state (every slot a colon) does not repeat the tensor: the Index row says every slot is a colon: the selection is the whole tensor in one line and stays short.

§2 · The index as the expression — one control, new in core

The picked control, T[ _, _, _ ], rendered as one line in the rail: the brackets and commas are text, each slot is a compact menu button showing its current value (: or a position) with the dimension's name in small type under it; pressing a slot opens the short list of positions for that dimension. Four slots fit the 300px rail at rank 4 with room to spare, because a slot is as wide as one character. Arrow keys move between slots and change a slot's value, so the keyboard path is the same control. This is a new control type in widgets/core/controls.js (a composite that reads and writes several parameters, one per slot); it is a core change, so the full fingerprint suite runs after it and the change is gated on that.
